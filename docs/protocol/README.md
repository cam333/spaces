# Spaces session-control protocol (v1)

This is the human-readable reference for the WebSocket protocol a client
(including the future Rust TUI client) speaks to a Spaces node to snapshot
and control workspaces, panes, and agents. It is generated by hand and kept
honest by a CI gate (`npm run proto:docs`, see the bottom of this file) that
fails if a method in the runtime's dispatch table stops being documented
here.

The **machine-readable** source of truth for every frame shape is the
generated JSON Schema at
[`docs/protocol/spaces-proto.schema.json`](./spaces-proto.schema.json)
(`npm run proto:schema` / `npm run proto:check`). None of the underlying Zod
schemas use `.strict()` — the server silently tolerates unknown request keys,
and the exported JSON Schema deliberately sets `additionalProperties: true`
on every object to match that leniency, so a generated client (Rust
`serde_json` or otherwise) never hard-rejects a payload the server actually
accepts, including additive v1 fields added later. When this document and
the schema disagree, the schema — and the runtime source it's generated from
(`bin/lib/runtime/protocol.js`, `bin/lib/runtime/index.js`,
`bin/lib/runtime/control-channel.js`, `bin/lib/runtime/pane-socket.js`) —
wins.

## Endpoints

Both endpoints are served on the same port as the legacy `/ws` terminal
endpoint: the main Spaces port (3457 by default, or the port this account
was given — see `spaces --help`). Only when `bin/terminal-server.js` runs on
its own, as in development and some tests, does it listen on
`SPACES_WS_PORT` (default `3458`) instead. Every connection must
authenticate; see "Threat model" in SECURITY.md.

| Endpoint | Transport | Purpose |
|---|---|---|
| `/proto` | WebSocket, JSON text frames both ways | Control channel: `hello` handshake, request/response method calls, live event stream. |
| `/proto/pane/<id>` | WebSocket, binary frames down / JSON text frames up | Pane data channel: raw PTY bytes streamed to the client, small JSON up-frames (input, resize) back. |

**Standing restriction (Phase 1):** both endpoints refuse the connection
outright — the TCP upgrade is destroyed before any handshake — when
`SPACES_MULTIUSER=1`. Neither `checkProtoAuth()` (which only proves the
caller holds *some* valid session/terminal token) nor the runtime itself
currently records which user opened a pane, so under multiuser mode nothing
stops one authenticated user from snapshotting, reading, or fully taking
over (`?takeover=1`) another user's pane. Until per-pane ownership is
threaded through `registerPane` and enforced in dispatch/pane-socket
filters, both `/proto` routes are refused entirely in multiuser mode rather
than exposed with that gap open. This is a Phase-1 restriction, not a
permanent protocol feature — expect it to be lifted once ownership lands.

**Authentication** (same for both endpoints). The server answers its
owner and nobody else; arriving on the loopback interface proves nothing,
since every account on the machine shares it. A client presents one of:

- `Authorization: Bearer <token>`, where the token is either the owner's
  secret (`~/.spaces/internal_token`, readable only by the owner) or a
  session token signed with it — which is what `spaces tui` and
  `spaces --remote` hand the terminal client, so the secret itself never
  leaves its machine. `x-spaces-internal: <secret>` is accepted too.
- The browser's `spaces-desktop` session cookie (HttpOnly, SameSite=Strict),
  which `spaces web` obtains through a single-use, two-minute sign-in link.

Credentials are read from headers only — never from the query string, where
they would end up in logs and histories. A multiuser session cookie or
terminal token is not a desktop credential, even if one is still valid.

Before any of that, the `Host` header must name the loopback (`localhost`,
`127.0.0.1`, `[::1]`, any port) or a host listed in
`SPACES_ALLOWED_ORIGINS`; anything else is refused, which is what stops a
web page that rebinds its own hostname to 127.0.0.1. The same rules guard
the web app's HTTP API.

An unauthenticated socket that completes the WS upgrade is sent a single
`error` frame with `code: "unauthorized"` and closed immediately.

## Handshake (control channel only)

The **first** frame a client sends on `/proto` must be a `Hello` frame, or
the socket is closed. The server does not read anything from `client` (it's
free-form, for the client's own logging/debugging), but `type` and
`protocolVersion` are validated:

```json
{ "type": "hello", "protocolVersion": 1, "client": "my-rust-client/0.1" }
```

`PROTOCOL_VERSION` is currently `1` (`bin/lib/runtime/protocol.js`). Five
outcomes, and the first two are **not** the same error even though they
sound similar — the `id` field differs, which matters if a client keys
retry logic off it:

- **The frame itself isn't valid JSON** → caught by the outer `JSON.parse`
  try/catch before the hello check ever runs, so this reply always has
  `id: "unknown"`, regardless of handshake state: `{"id":"unknown","error":{"code":"bad_request","message":"invalid json"}}`, socket stays open.
- **Valid JSON, but doesn't match the `Hello` shape** (wrong `type`, missing/wrong-typed `protocolVersion` or `client`, etc.) → `{"id":"hello","error":{"code":"bad_request","message":"expected hello"}}`, socket stays open (the client may retry within the hello window).
- **Valid `Hello` but `protocolVersion` doesn't match the server's** → a *typed* error, not a generic parse failure: `{"id":"hello","error":{"code":"version_mismatch","message":"runtime speaks protocol 1"}}`, then the socket is closed.
- **No valid hello within 5000ms of connecting** → `{"id":"hello","error":{"code":"bad_request","message":"hello timeout"}}`, socket closed.
- **Success** → `{"type":"hello-ok","protocolVersion":1,"nodeId":"<node id>","seq":<current event seq>}`. Only after this may `Request` frames be sent.

## Requests and responses (control channel)

Every subsequent client frame is a `Request`:

```json
{ "id": "r1", "method": "session.snapshot", "params": {} }
```

- `id`: any non-empty string, echoed back verbatim so the client can
  correlate responses. It is not required to be unique server-side.
- `method`: one of the method names in the [method reference](#method-reference) below.
- `params`: an object (default `{}` if omitted; a literal `null` is also
  normalized to `{}`).

A frame that doesn't parse as JSON, or doesn't match the `Request` shape,
gets `{"id":"<echoed id or "unknown">","error":{"code":"bad_request","message":"invalid json"|"invalid request"}}`.
Otherwise the server replies with exactly one of:

```json
{ "id": "r1", "result": { /* method-specific */ } }
{ "id": "r1", "error": { "code": "not_found", "message": "no pane p1" } }
```

### Error codes

The full protocol error-code enum (`ERROR_CODES` in `protocol.js`):

| Code | Meaning |
|---|---|
| `bad_request` | Malformed frame or invalid/missing params. |
| `unauthorized` | Socket never authenticated. |
| `not_found` | Referenced pane/workspace doesn't exist. |
| `conflict` | Pane control slot already held (data channel); also the wait/timeout mapping below. |
| `version_mismatch` | Hello's `protocolVersion` didn't match the server's. |
| `gap` | Reserved for future use — not currently emitted by any method (see `events.subscribe`'s `gap` result field, which is a boolean on a *successful* response, not this error code). |
| `internal` | Unexpected server-side failure (DB error, spawn failure, etc). |

### Async methods (`agent.wait`, `agent.prompt-wait`, `detect.update`)

Three methods — `agent.wait`, `agent.prompt-wait`, `detect.update` — are
asynchronous and are intercepted by the control channel **before** they ever
reach the synchronous dispatch table, so they must be invoked as an ordinary
`Request` over `/proto` exactly like every other method (the control channel
itself awaits the promise and replies once it settles; there is no separate
"async" framing on the wire). Calling any of these through synchronous
dispatch (e.g. a test harness or a future non-WS embedding calling
`runtime.dispatch()` directly instead of going through the control channel)
returns an honest error instead of lying with a fabricated synchronous
result:

```json
{ "error": { "code": "bad_request", "message": "agent.wait is asynchronous; call it over the control channel" } }
```

For `agent.wait` and `agent.prompt-wait` specifically, a failed wait is
mapped from the runtime's internal outcome code onto the protocol's existing
error-code enum — **`timeout` and `agent_prompt_stalled` are not members of
`ERROR_CODES`**; both are folded onto `conflict`, with the original word
preserved as a prefix on the message so the client can still distinguish
them:

| Runtime outcome code | Protocol error code | Example message |
|---|---|---|
| `bad_request` | `bad_request` | `bad_request: paneId must be a non-empty string` |
| `not_found` | `not_found` | `not_found: no pane p1` |
| `timeout` (agent.wait only) | `conflict` | `timeout: pane p1 did not reach blocked in 3000ms` |
| `agent_prompt_stalled` (agent.prompt-wait only) | `conflict` | `agent_prompt_stalled: no lifecycle change within 5000ms` |
| anything else | `internal` | `internal: <error message>` |

## Events

`events.subscribe` is the one control-channel method that is **not** part of
the synchronous dispatch table and does **not** appear in `node.methods`'
`sync`/`async` lists — it is handled entirely inside the control channel
itself, both because its reply shape (`{gap, events}`) is unlike every other
method's, and because a successful call also puts the socket into a
different mode (live event push) for the rest of its lifetime.

```json
{ "id": "r1", "method": "events.subscribe", "params": { "afterSeq": 0 } }
```

- `afterSeq` (optional, non-negative integer, default `0`): the last event
  sequence number the client has already applied. A present-but-invalid
  value (non-integer or negative) is rejected with `bad_request` rather
  than silently coerced (a coerced `NaN` previously produced a false
  "you're fully caught up" backlog) — only a genuinely *missing* `afterSeq`
  falls back to `0`.

Reply:

```json
{ "id": "r1", "result": { "gap": false, "events": [ /* EventFrame.event[] */ ] } }
```

- `events`: every buffered event with `seq > afterSeq` (the server keeps a
  512-event ring buffer).
- `gap`: `true` when `afterSeq` predates the oldest event still in the ring
  — the requested backlog is incomplete, and **the client must discard its
  incremental state and re-fetch a fresh `session.snapshot` instead of
  applying `events` as deltas**. `gap: false` means `events` is a complete,
  contiguous backlog safe to apply in order.

After the reply, the **same socket** starts receiving every future event
individually, each as its own frame (no `id`, since these are pushes, not
replies to a specific request):

```json
{ "event": { "seq": 42, "type": "pane.state", "payload": { "paneId": "p1", "agentState": "working", "seen": true }, "ts": 1735689600000 } }
```

A second `events.subscribe` call on the same socket replaces the previous
live subscription (only one is active per socket at a time).

Event `type` is one of: `pane.opened`, `pane.closed`, `pane.state`,
`pane.seen`, `pane.title`, `pane.updated`, `pane.session`, `pane.notify`,
`pane.created`, `pane.removed`, `workspace.created`, `workspace.updated`,
`workspace.removed`, `pane.moved`. `payload` is event-specific (see
`EventFrame` in the [JSON Schema](./spaces-proto.schema.json) for exact
per-type shapes where captured, and the method reference below for which
methods emit which event types).

### Changes made outside the runtime

The web app writes the same database from its own process. The runtime
notices those writes (it polls SQLite's `data_version`, which moves only for
commits by another connection) and replays them as the events above, so a
client sees a space renamed in the browser within about half a second
without resnapshotting:

- a new space → `workspace.created`, then `workspace.updated` with its
  `color` (which `workspace.created` does not carry);
- a renamed or recoloured space → `workspace.updated`;
- a deleted space → `workspace.removed`, with the panes it took in
  `closedPanes`;
- a new pane row → `pane.created` with `live: false` (the row exists, no
  process does yet), then `pane.updated` with its `title` and `color`;
- a renamed or recoloured pane → `pane.updated`; a rename is a user title,
  so the pane's shell cannot overwrite it;
- a pane moved between spaces → `pane.moved`;
- a deleted pane row → `pane.removed`, unless the pane is still running, in
  which case its exit reports it.

If an outside write and one of the runtime's own land within the same poll,
the runtime's change can be announced twice. Every event above is
idempotent to fold, and a running pane is never re-announced, so a client
needs no de-duplication.

### A space's git status

`workspace.updated` also carries `git` when the working copy behind a space
changes: `{ branch, ahead, behind, dirty }`, or `null` when the space is no
longer in a repository. The directory is the space's first pane's `cwd`;
the runtime refreshes it every few seconds off the request path.

## Pane data channel (`/proto/pane/<id>`)

```
GET /proto/pane/<paneId>?mode=control&takeover=1
```

- `mode` — `control` (default is `observe` if omitted or any other value).
  A `control` attach claims the pane's single controller slot; only the
  current controller's up-frames are accepted. `observe` never claims
  control — its up-frames are rejected with `bad_request` (`"observer
  cannot send input"`).
- `takeover=1` — only meaningful with `mode=control`. Without it, a second
  simultaneous control attach is refused with `{"type":"error","code":"conflict","message":"pane already controlled"}` and the socket is closed. With `takeover=1`, the new
  socket demotes the previous controller: the previous controller's own
  socket receives `{"type":"error","code":"conflict","message":"taken over by another client"}` (it is not closed — it silently drops to observer-like status: it keeps
  receiving PTY output but can no longer send input) and the new socket
  becomes the sole controller.
- A pane that doesn't exist (no live PTY registered) is refused up front:
  `{"type":"error","code":"not_found","message":"no live pane <id>"}`, then closed. An unauthenticated socket gets `code: "unauthorized"`.

**Attach sequence**, once accepted:

1. Text frame `{"type":"replay-start"}`
2. One **binary** frame: the pane's current screen state serialized as ANSI
   (xterm's own serializer output — colors and scrollback), so a freshly
   attached client can repaint immediately without replaying history itself.
3. Text frame `{"type":"replay-end"}`
4. From then on: every live PTY chunk as its own binary frame, as it's
   produced, indefinitely.
5. If the pane's process exits while the socket is attached: text frame
   `{"type":"exit","exitCode":<n>}`, then the socket is closed.

**Up-frames** (JSON text only — a binary up-frame gets
`{"type":"error","code":"bad_request","message":"up-frames are json text"}`),
only accepted from the controller:

```json
{ "t": "i", "data": "ls -la\n" }
{ "t": "r", "cols": 120, "rows": 40 }
```

- `t: "i"` — raw bytes to write to the PTY's stdin.
- `t: "r"` — resize the PTY (`cols`/`rows` must be positive integers).

Any other down-frame is `{"type":"error","code":"<ERROR_CODES member>","message":"..."}`
(see the error-codes table above).

## Workspace ids on the wire

The canonical public form for a workspace id is `w<rowid>` (e.g. `"w12"` for
the workspace with database row id `12`), and every id returned by
`session.snapshot`, `workspace.create`, and every event payload is in this
exact form.

**Parsing is looser than that, and worth knowing precisely.** Every method
that takes a `workspaceId` param resolves it with `workspaceRowId()`
(`bin/lib/runtime/index.js`), which is the regex `/^w(\d+)$/` applied to the
raw string — it captures the digits and does not require they be in
canonical (no-leading-zero) form. So `"w01"` **is accepted** and resolves to
row `1`, same as `"w1"` — it is not rejected. Only something that doesn't
match the pattern at all (a bare number, `"w"` with no digits, garbage) gets
`bad_request`.

Because of that leniency, **what a method echoes back is not always the
canonical form** — every method that returns or emits a workspace id rebuilds
`` `w${rowId}` `` from the parsed row id before putting it on the wire
(`workspace.create`, `workspace.update`, `workspace.close`, `pane.move`, and
`pane.create` all do this), so a non-canonical input to any of them still
comes back canonical. A client that calls `pane.create` with
`workspaceId: "w01"` gets `workspaceId: "w1"` back from that call — the same
canonical form a later `session.snapshot` reports for the same pane — so ids
can safely be compared with `===` across a `pane.create` result and a
subsequent snapshot/event.

## Method reference

`node.methods` (see below) is the runtime's own live listing of every
dispatchable method name, split into `sync` and `async`; this reference
covers the same 21-method set, described for a client author. Every method
below is invoked as a `Request` over the `/proto` control channel; none of
them exist on the pane data channel.

Params marked **required** cause `bad_request` if missing or the wrong
type. Unless stated otherwise, a method requires the referenced pane to be
*live* (still has a running PTY, not just a DB row) and returns `not_found`
if not.

---

### `session.snapshot`

Full point-in-time view of every workspace and pane, merging the DB (if
`spacesDbPath` is configured and readable) with the runtime's own live
state. Used to (re)build client-side state from scratch, and to resync
after `events.subscribe` reports `gap: true`.

A workspace or pane torn down via `pane.close`/`workspace.close` is entirely
absent from this result afterward — not listed with `live: false`, and not
resurrected as a nameless stub workspace — since a protocol-initiated close
has nothing "recently exited" worth showing. A pane whose PTY exited on its
own (not via `pane.close`/`workspace.close`) still appears with `live: false`
so a client can show it "recently exited", the same as before.

- **Params:** none.
- **Result:**
  ```
  {
    protocolVersion: 1,
    nodeId: string,
    seq: number,               // current event hub sequence
    workspaces: WorkspaceInfo[],  // { id, name, color, paneIds, git? }
    panes: PaneInfo[],            // { id, workspaceId, agentType, agentState, seen, title, cwd, sessionRef, live }
  }
  ```
- **Errors:** none — always succeeds (DB unavailable degrades to a
  runtime-only view rather than erroring).

### `node.info`

Cheap in-memory identity/liveness check (no DB access) — the control
channel itself calls this internally to build the `hello-ok` reply.

- **Params:** none.
- **Result:** `{ nodeId: string, protocolVersion: 1, seq: number }`.
- **Errors:** none.

### `node.methods`

The runtime's own live method catalogue. `sync` is every method dispatchable
through the synchronous switch (including the async ones themselves — see
below); `async` is the subset that must actually be awaited rather than
called synchronously.

- **Params:** none.
- **Result:** `{ protocolVersion: 1, sync: string[] (sorted), async: string[] (sorted) }`.
- **Errors:** none.

### `pane.focus`

Marks one pane focused and every other pane unfocused (exclusive — at most
one pane is ever focused at a time). Focusing a pane also marks it "seen",
which affects the `done` state rollup (a completed-but-unseen pane can
render as "done" again once it loses focus and later completes again).

- **Params:** `paneId` (string, **required**).
- **Result:** `{ ok: true }`.
- **Errors:** `bad_request` (missing paneId), `not_found` (no such pane —
  checked against the state store, not liveness, so this works even for a
  pane whose PTY has exited).

### `pane.read`

Read the pane's current terminal screen without attaching a data-channel
socket.

- **Params:** `paneId` (string, **required**); `source` (string, optional,
  `"visible"` (default) or `"detection"`).
- **Result:** `source: "visible"` → `{ rows: string[] }` (one string per
  visible row, scrollback excluded). `source: "detection"` → `{ rows: string[], title: string, progress: string|null, cols: number, rows_count: number }`.
- **Errors:** `bad_request` (missing paneId), `not_found` (no *live* screen
  for that pane).

### `pane.input`

Write raw bytes to a live pane's PTY stdin (equivalent to the data
channel's `{t:"i"}` up-frame, but over the control channel and without
needing to hold the controller slot).

- **Params:** `paneId` (string, **required**); `data` (string, **required**).
- **Result:** `{ ok: true }`.
- **Errors:** `bad_request` (missing paneId or non-string data),
  `not_found` (pane not live).

### `pane.resize`

- **Params:** `paneId` (string, **required**); `cols`, `rows` (positive
  integers, both **required** — a float, string, `NaN`, zero, or negative
  value is rejected rather than truncated).
- **Result:** `{ ok: true }`.
- **Errors:** `bad_request` (missing paneId, or cols/rows not positive
  integers), `not_found` (pane not live).

### `pane.create`

Creates a DB-backed pane row and spawns its PTY in one call. On any failure
after the DB row is written (spawn failure, or runtime registration
failure), the row is rolled back — never orphaned.

- **Params:**
  - `workspaceId` (string, **required**, canonical `"wN"` form).
  - `cols` (positive integer, default `120`).
  - `rows` (positive integer, default `30`).
  - `agentType` (string, default `"shell"`) — one of the launch-table keys
    (`shell`, `claude`, `codex`, `gemini`, `aider`, `forge`, `pi`, `custom`)
    or any other string. An unrecognized value has no launch command,
    same as `"shell"` — but it is **not** identical to `"shell"` on
    Windows: the shell-selection logic routes any `agentType !== "shell"`
    (including an unrecognized one) through Git Bash, while a literal
    `"shell"` gets `cmd.exe`.
  - `cwd` (string, default the server process's home directory).
  - `title` (string, default: same as `agentType`).
  - `customCommand` (string, optional) — the command line typed in when
    `agentType` is `"custom"`.
  - `agentSession` (string, optional) — a session id to resume; only
    applies to agent types with a `resumeFlag` (`claude`, `codex`, `gemini`,
    `forge`, `pi`) and only when not the literal string `"new"`.
- **Result:** `{ paneId: string (uuid), workspaceId: string, agentType: string, cwd: string, launchCommand: string }`.
  `launchCommand` is the command line that will be typed into the fresh
  pane (or `""` for a plain shell/unrecognized agent type — `pane.create`
  itself does not type it in; `agent.start` does that for an
  already-created pane).
- **Emits:** `pane.created` (payload: `{ paneId, workspaceId, agentType,
  cwd }`). The same event with `live: false` announces a pane row added
  outside the runtime; absent means live.
- **Errors:** `bad_request` (missing/malformed `workspaceId`, or non-integer/non-positive `cols`/`rows`), `not_found` (workspaceId doesn't reference an existing workspace), `internal` (PTY spawn failure or a runtime registration failure after a successful spawn — the PTY is killed and the DB row rolled back either way).

### `pane.close`

Kills the pane's live PTY (if any) and deletes its DB row (if any).
`not_found` only when **neither** existed. The pane's runtime state record is
also dropped entirely (not merely marked closed), so it stops appearing in
`session.snapshot` — see that method's note above.

- **Params:** `paneId` (string, **required**).
- **Result:** `{ ok: true }`.
- **Emits:** `pane.removed`.
- **Errors:** `bad_request` (missing paneId), `not_found` (no live pane and
  no DB row for that id).

### `fs.folders`

Lists one level of folders on this machine, for a client's directory browser.
Confined to the user's dev directories (`devDirectories` in
`~/.spaces/config.json`, or the home directory when none are set), the same
rule as the web app's folder picker. Symlinks are resolved before the check,
so one cannot lead outside. Hidden folders and `node_modules` are left out.
Not available over federation: a peer cannot browse this machine.

- **Params:** `path` (string, optional; default the first dev directory).
- **Result:** `{ current, parent, folders: [{ name, path }], roots }`, where
  `parent` is `null` at the top of a dev directory and `roots` lists every
  dev directory.
- **Errors:** `bad_request` (path not a string, or outside the dev
  directories), `not_found` (no such folder, unreadable, or no dev directory
  exists).

### `fs.list`, `fs.read`, `fs.write`, `fs.mkdir`, `fs.move`, `fs.delete`

The file browser's operations, on the machine this runtime runs on. Confined
like the web app's file viewer: the dev directories (or the home directory
when none are set) plus the agent transcript stores (`~/.claude/projects`,
`~/.codex/sessions`, `~/.gemini/tmp`). Always refused, even inside an allowed
folder: `~/.spaces`, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.azure`, `~/.kube`,
`~/.docker`, `~/.config/gcloud`, `~/.config/gh`, `~/.netrc`, `~/.npmrc`,
`~/.pypirc`, `~/.git-credentials`, and the rest of `~/.claude`, `~/.codex`
and `~/.gemini`. Paths are checked after resolving symlinks; `fs.delete` and
`fs.move` act on a link itself, never its target, and never on a root. Not
available over federation. A refused path is `bad_request`; an existing
target, or a file changed since it was opened, is `conflict`.

- **`fs.list`** `{ path? }` → `{ current, parent, entries: [{ name, path,
  type, size, mtime }], truncated, roots }`. Folders first. `type` is `dir`,
  `file`, `link-dir`, `link-file`, `link-broken` or `other`. At most 5000
  entries. `parent` is `null` at a root. Defaults to the first dev directory.
- **`fs.read`** `{ path, offset?, length? }` → `{ path, size, mtime, offset,
  data, eof }`. `data` is base64, at most 1 MiB per call.
- **`fs.write`** `{ path, data, mode?, expectMtime? }` → `{ path, size,
  mtime }`. `data` is base64, at most 1 MiB decoded. `mode`: `create`
  (default; must not exist), `truncate` (create or replace), `append` (must
  exist). With `expectMtime`, a file modified since is refused.
- **`fs.mkdir`** `{ path }` → `{ path }`. One level; an existing folder is
  `conflict`.
- **`fs.move`** `{ from, to, overwrite? }` → `{ path }`. Rename or move;
  refuses an existing target unless `overwrite`, and a folder into itself.
- **`fs.delete`** `{ path }` → `{ ok: true }`. Folders are removed with
  everything in them; the client confirms first.

### `pane.restart`

Starts a stopped pane again in place: same id, workspace, directory and
agent. A server restart or a reboot stops every pane while their rows
survive, and `session.snapshot` reports them with `live: false`; this is how a
client brings one back. The runtime types the pane's launch command itself,
so no `agent.start` follows. A Claude pane resumes its recorded conversation
only when that transcript still exists; otherwise it starts fresh. A
directory that no longer exists falls back to the home directory.

- **Params:** `paneId` (string, **required**); `cols`, `rows` (positive
  integers, optional, default 120x30).
- **Result:** `{ paneId, workspaceId, agentType, cwd, resumed, launchCommand }`.
- **Emits:** `pane.opened`.
- **Errors:** `bad_request` (missing paneId, bad size, or the pane is already
  running), `not_found` (no row for that id), `internal` (spawn failed).

### `pane.move`

Reassigns a pane to a different workspace (updates the DB row; the live
in-memory record is kept in sync so the next `session.snapshot` agrees).

- **Params:** `paneId` (string, **required**); `workspaceId` (string,
  **required**, canonical `"wN"` form — the *destination* workspace).
- **Result:** `{ ok: true }`.
- **Emits:** `pane.moved` (payload: `{ paneId, workspaceId }`, the
  canonical destination id).
- **Errors:** `bad_request` (missing paneId or malformed workspaceId),
  `not_found` (no such pane or no such destination workspace), `internal`.

### `pane.update`

Renames or recolours a pane. A title set here is a *user* title: it wins
over every later OSC title the pane's shell emits.

- **Params:** `paneId` (string, **required**); `title` (string, optional —
  trimmed; the empty string hands the pane back to its shell's own title,
  which is the only way to undo a rename); `color` (optional — a non-empty
  string sets it, anything else clears it). At least one of `title`/`color`.
- **Result:** `{ ok: true, ...writtenFields }`.
- **Emits:** `pane.updated` (payload: `{ paneId, title }` and/or
  `{ paneId, color }`, one event per field).
- **Errors:** `bad_request` (missing paneId, non-string title, or neither
  field), `not_found` (no such pane row), `internal`.

### `session.list`

The agent sessions a directory already has, newest first, so a client can
offer to resume one when starting an agent there.

- **Params:** `cwd` (string, **required**); `agentType` (string,
  **required**); `limit` (positive integer, optional, default 20, max 100).
- **Result:** `{ sessions: [{ sessionId, label, messageCount, modified,
  gitBranch, agentType }] }`. Empty for an agent that cannot resume, or
  when the web app has not indexed any sessions yet.
- **Errors:** `bad_request` (missing `cwd` or `agentType`).

### `net.peers`, `net.pair`, `net.forget`, `net.snapshot`, `net.request`

The fleet methods, for reaching panes on other machines. Federation is
shelved: these exist in the dispatch table, but no shipped client uses
them and they may change.

- `net.peers` — no params; `{ nodes }`, the paired machines. Carries no
  key material.
- `net.pair` — `url`, `publicKey` (**required**), `name`, `apiKey`,
  `nodeId` (optional); `{ node }`. `bad_request` on any pairing failure.
- `net.forget` — `nodeId` (**required**); `{ ok }`.
- `net.snapshot`, `net.request` — asynchronous, handled by the control
  channel itself (a synchronous dispatch answers `bad_request`): a peer's
  snapshot, or one method call forwarded to it (`nodeId`, `method`,
  `params`).

### `workspace.create`

- **Params:** `name` (string, **required**, non-blank after trimming —
  stored trimmed); `color` (string, optional; checked with the same
  "non-empty string" predicate as every other string param in this
  protocol, not a bare `typeof === 'string'` check — so `null`, any
  non-string value, **and an empty string `""`** all clear it to `null`
  rather than being stored as given).
- **Result:** `{ workspaceId: string }` (canonical `"wN"` form).
- **Emits:** `workspace.created` (payload: `{ workspaceId, name }`).
- **Errors:** `bad_request` (missing/blank name), `internal` (DB failure).

### `workspace.update`

At least one of `name`/`color` must be present.

- **Params:** `workspaceId` (string, **required**, `"wN"` form); `name`
  (string, optional — must be non-blank if provided); `color` (optional —
  same non-empty-string-or-else-null rule as `workspace.create`, including
  the empty-string case).
- **Result:** `{ ok: true }`.
- **Emits:** `workspace.updated` (payload: `{ workspaceId, ...changedFields }`).
- **Errors:** `bad_request` (malformed workspaceId, blank name, or neither
  field supplied), `not_found` (no such workspace), `internal`.

### `workspace.close`

Deletes the workspace and every pane row under it, and kills every live PTY
belonging to it (both DB-known pane rows and any live-but-not-yet-persisted
pane the runtime itself is tracking under that workspace id — the two sets
are unioned into `closedPanes`). Existence is verified, and the DB delete is
committed, **before** any PTY is touched: a `not_found` or `internal`
response is a guarantee that nothing was killed and nothing was deleted.
Every pane's runtime state record under this workspace is also dropped
entirely, so neither the workspace nor its panes are resurrected as a
nameless stub by a later `session.snapshot` — see that method's note above.

The same transaction remembers the workspace in the runtime's own
`closed_workspaces` table: its name, color, and each pane's agent, folder,
title and Claude conversation, in tab order. So a close either deletes and
remembers, or does neither. See `workspace.closedList`. A workspace the web
app deletes itself is not remembered.

- **Params:** `workspaceId` (string, **required**, `"wN"` form).
- **Result:** `{ ok: true, closedPanes: string[], closedKey: string }`
  (every pane id that was actually torn down, and the key of the record
  that remembers the workspace).
- **Emits:** `workspace.removed` (payload: `{ workspaceId, closedPanes, closedKey }`).
- **Errors:** `bad_request` (malformed workspaceId), `not_found` (no such
  workspace — e.g. it was already deleted out-of-band by the web app, which
  shares the same `spaces.db`), `internal` (DB failure).

### `workspace.closedList`

Every workspace closed on this machine through `workspace.close`, newest
first, so a client can offer one back. There is no cap: a record stays until
a client forgets it.

- **Params:** none.
- **Result:** `{ closed: [{ key, name, color, closedAt, tabs: [{ agentType,
  cwd, title, claudeSessionId }] }] }`. `closedAt` is an ISO 8601 time;
  `color`, `cwd`, `title` and `claudeSessionId` may be null.
- **Errors:** `internal` (DB unavailable).

Reopening is the client's: `workspace.create` with the record's name and
color, `pane.create` per tab in its folder (with `agentSession` set to the
tab's `claudeSessionId` to resume that conversation, when its transcript is
still there), then `workspace.closedForget` with the record's key.

### `workspace.closedForget`

Forgets one closed workspace: once a client has reopened it, or the user
removed it from the list.

- **Params:** `key` (string, **required**).
- **Result:** `{ ok: true }`.
- **Errors:** `bad_request` (missing key), `not_found` (no such record),
  `internal` (DB failure).

### `agent.start`

Types a launch command into an already-live pane (created via `pane.create`
with `agentType: "shell"`, or reused). Does **not** apply to `agentType:
"shell"` or an unrecognized type — those have no launch command by
definition and return `bad_request`; use `"custom"` with `customCommand`
for an arbitrary command line.

- **Params:** `paneId` (string, **required**, must already be live);
  `agentType` (string, **required**) — one of `claude`, `codex`, `gemini`,
  `aider`, `forge`, `pi` (each has a built-in command), or `custom` (uses
  `customCommand` verbatim); `agentSession` (string, optional, resume
  target — same `resumeFlag`/`"new"` rules as `pane.create`);
  `customCommand` (string, optional, required in practice for
  `agentType: "custom"` — an empty/absent one also yields `bad_request`).
- **Result:** `{ ok: true, launchCommand: string }`.
- **Errors:** `bad_request` (missing paneId/agentType, or the resolved
  agentType+customCommand combination produces an empty launch command),
  `not_found` (paneId not live).

### `agent.prompt`

Writes a prompt string into a live pane, without waiting for any response
(fire-and-forget — pair with `agent.prompt-wait` for a version that waits).

- **Params:** `paneId` (string, **required**, live); `text` (string,
  **required**, may be empty); `bracketedPaste` (boolean, optional, default
  `false` — wraps the text in bracketed-paste escapes so a multi-line prompt
  isn't interpreted line-by-line by the target's readline).
- **Result:** `{ ok: true }`.
- **Errors:** `bad_request` (missing paneId or non-string text), `not_found`
  (paneId not live).

### `agent.wait` (async)

Resolves once the pane's agent state enters one of `until`, or times out.
**Must be called over the control channel** — see
[Async methods](#async-methods-agentwait-agentprompt-wait-detectupdate)
above; a synchronous `dispatch()` call returns `bad_request`.

- **Params:** `paneId` (string, **required**); `until` (array of
  `"working"|"blocked"|"idle"|"unknown"`, **required**, non-empty — any
  unrecognized state name is `bad_request`); `timeoutMs` (positive integer,
  optional, default `30000`, clamped to a maximum of `300000`).
- **Result (success):** `{ ok: true, state: string }` — resolves
  immediately if the pane is already in one of the target states.
- **Result (failure, see the [async error-code mapping](#async-methods-agentwait-agentprompt-wait-detectupdate)):**
  `bad_request` (bad paneId/until), `not_found` (no such pane), `conflict`
  with a `timeout:`-prefixed message (deadline passed with no matching state
  change), `internal` (unexpected failure subscribing to the event hub).

### `agent.prompt-wait` (async)

Writes a prompt (same encoding as `agent.prompt`) and resolves on the
**first** subsequent agent-state change of any kind — unlike `agent.wait`,
there is no `until` list; any transition satisfies it. **Must be called over
the control channel**, same as `agent.wait`.

- **Params:** `paneId` (string, **required**, live); `text` (string,
  **required**); `bracketedPaste` (boolean, optional, default `false`);
  `timeoutMs` (positive integer, optional, default `5000`, clamped to a
  maximum of `300000`).
- **Result (success):** `{ ok: true, state: string }`.
- **Result (failure):** `bad_request` (bad paneId/text), `not_found` (pane
  not live — checked both before writing and if the write itself reports
  failure), `conflict` with an `agent_prompt_stalled:`-prefixed message (no
  lifecycle change within the deadline), `internal`.

### `detect.explain`

Debug/inspection view of the detection engine's current verdict for one
pane — which rule fired, what evidence it saw, and which manifest is in
effect.

- **Params:** `paneId` (string, **required**).
- **Result:**
  ```
  {
    paneId: string, agentType: string, agentState: string, seen: boolean,
    detected: { state: string, ruleId: string, reason: string, at: number },
    manifest: { agent: string, version: string, source: "user"|"cache"|"bundled" } | null,
    pendingIdle: <scheduler-defined>,
    evidence: <rule-defined>,
  }
  ```
- **Errors:** `bad_request` (missing paneId), `not_found` (no pane, or no
  detection result yet computed for it).

### `detect.manifests`

Lists every currently-loaded agent-detection manifest and where it came
from (source precedence is user override > remote cache > bundled).

- **Params:** none.
- **Result:** `{ engineVersion: number, manifests: { agent: string, version: string, source: "user"|"cache"|"bundled" }[] }`.
- **Errors:** none.

### `detect.reload`

Forces the manifest registry to re-read every manifest directory from disk
(picks up manually-dropped files without a restart).

- **Params:** none.
- **Result:** `{ loaded: string[] (agent ids), skipped: { agent: string, source: string, error: string }[] }`.
- **Errors:** none.

### `detect.update` (async)

Fetches the published manifest index over HTTPS and refreshes any
out-of-date cached manifests. Never rejects — a failed refresh just leaves
the previous manifests in place, reported in `skipped`. **Must be called
over the control channel**; see
[Async methods](#async-methods-agentwait-agentprompt-wait-detectupdate)
above.

- **Params:** none (the index URL and cache directory are server
  configuration, not caller-supplied).
- **Result:** `{ updated: string[] (agent ids that were refreshed), skipped: { agent: string, reason: string }[] }`. If the server was started with `SPACES_NO_DETECTION_UPDATE=1`, this resolves immediately with `{ updated: [], skipped: [{ agent: "*", reason: "updates disabled" }] }` instead of making any network call.
- **Errors:** `internal` only if the refresh promise itself rejects
  unexpectedly (the normal not-updated/failed-fetch cases are reported in
  `skipped`, not as a protocol error).

## Keeping this document honest

`scripts/check-protocol-docs.mjs` reads the committed method catalogue
(`tests/proto/fixtures/method-catalogue.json`, the same fixture
`tests/proto/contract.test.ts` checks `node.methods`' live response
against) and fails if any of its `sync` method names is not a literal
substring of this file. Run it with:

```
npm run proto:docs
```

It's wired into CI (`.github/workflows/ci.yml`) immediately after the
protocol schema drift check, so a method added to the runtime's dispatch
table without a matching section here fails the build.

**What this gate does and does not prove.** It only checks that every
catalogued method *name* appears somewhere in this file as a substring —
that's all `doc.includes(m)` can see. It cannot tell whether a method's
name merely appears in a sentence versus a real, correct section; it
cannot detect a wrong param name, a wrong default value, a wrong result
shape, or an error code this document invented that the runtime doesn't
actually return. A method could be "documented" with an entirely fabricated
signature and this check would still pass. The accuracy of everything above
this line rests on manual review against the runtime source
(`bin/lib/runtime/`), not on this gate — treat it as a coverage floor
("nothing was silently dropped"), not a correctness guarantee.
